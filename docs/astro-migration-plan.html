Step 1 — Repo strategy (decided)

  • New repo 314_astro (already created by Lyudmil).
  • Reason: CodeKit scans the whole project folder — putting node_modules/, package.json, astro.config.mjs inside 314_snq risks CodeKit trying to process them (and recompiling on every save).
  • 314_snq stays untouched until the Astro site is verified live.

Two options — A keeps the separate pages repo (needs a PAGES_TOKEN secret), B flips GH Pages onto 314_astro itself (no token, simpler). See §4 for the plain-language explanation.

Step 11 — Deploy pipeline (30 min)

Replaces the manual build/→pages-repo push. Add .github/workflows/deploy.yml in this repo:

name: Build & Deploy
on:
  push:
    branches: [main]
permissions:
  contents: write
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: peaceiris/actions-gh-pages@v4
        with:
          personal_token: ${{ secrets.PAGES_TOKEN }}   # fine-grained PAT, repo scope
          publish_dir: ./dist
          external_repository: <owner>/<pages-repo>
          publish_branch: main
  • Needs: pages repo name + PAGES_TOKEN secret (decision #2).
  • Simpler alternative: point GH Pages at iam314-astro itself + actions/deploy-pages (no token needed) — then CNAME in public/ keeps the domain.
  • Cutover = first successful workflow run. Keep 314_snq intact until then.

Pitfalls & gotchas

  1. Don’t co-locate Astro inside the CodeKit project (Step 1).
  2. is:inline for all third-party scripts — gtag, Payhip, Swiper, ConvertKit.
  3. OG image filenames contain spaces + & (e.g. Open Graph - The R&B Awards.png) — keep the exact strings from the .kit files; they work in HTML attributes and resolve live (verified).
  4. CNAME must stay in public/ so the deployed dist/ keeps the custom domain.
  5. Trailing slashes: keep trailingSlash: 'always'; both /work and /work/ 200 on GH Pages today.
  6. Dark-mode theming depends on color inheritance (.body-light.is-dark) for currentColor marks and text — preserve body class="body-light" in the layout.
  7. Payhip cart must load on every page (user decision) — do not scope it to product pages.
  8. Lottie: no eager script; lyudmils.js lazy loader handles it.
  9. Newsletter form JSON is now valid — don’t reintroduce the comma bug when copying.
  10. Jwax — deleted (page, thumb, work-index card). Ensure no leftover links/OG refs remain before cutover.

4. Open questions

  1. ~~How is build/ published?~~ Answered: separate pages repo, manual push.
  2. Deploy target — plain-language explanation (needed for Step 11):
  • Option A — keep the separate pages repo. The GH Actions workflow in 314_astro builds the site, then pushes the result to your existing pages repo (the one serving the site today). Because GitHub Actions is not allowed to write to another repo without permission, you must create a Personal Access Token (PAT) — a credential from github.com/settings/tokens — grant it permission for that pages repo, and paste it into 314_astro → Settings → Secrets and variables → Actions as a secret named PAGES_TOKEN. The workflow uses that secret to authenticate the push. Pros: zero changes to how the domain/pages repo work; only works if you’re comfortable creating a token. Cons: token setup, and tokens expire (you’d refresh it occasionally).
  • Option B — point GitHub Pages at 314_astro itself. Enable Pages on the new repo (Settings → Pages → Source: GitHub Actions), add the custom domain www.iam314.com there, and use GitHub’s built-in actions/deploy-pages step in the workflow. This needs no token at all — deploying to the same repo that runs the workflow is automatic. DNS does not change (the CNAME record already points at iam314.github.io), and the CNAME file in public/ keeps the domain attached. Cons: you retire the old pages repo (or leave it idle), and the custom domain gets re-verified on the new repo (instant, since DNS is already correct).
  • Recommendation: Option B — fewer moving parts, no secrets to maintain, one repo instead of two.
